# OMAP 查询性能优化方向

状态：M5 阶段的五个方向、M7 的向量化下推、M9 的数组列按元素列式存储与 M11 的段级剪枝、有序 `LIMIT` 均已交付。第四节到第五节是 `q4`（含两个 `CARDINALITY` 谓词的组合过滤）的定位过程与解决结果；第六节是段级剪枝与有序 `LIMIT` 在真实实例上的实测。

历史方向的逐条收益记录在 git 历史中（最后一次记录为 `384b768`，测量环境与本机不同，数值不可直接比较）。

## 二、改动前的实测结果

1000 万行、9 列、`segmentSize=65536`、`compactionMinRows=1`、`QUERY_CACHE_SIZE=0`、16 读线程 × 50 轮、独立 TCP 服务端进程 + 外部纯 H2 客户端进程。

| 查询 | 不限速写<br>（平衡电源） | 限速 50 轮/秒<br>（平衡电源） | 限速 50 轮/秒<br>（最佳性能） | 无写线程<br>（最佳性能） | 记录值<br>限速 50 轮/秒 |
| --- | --- | --- | --- | --- | --- |
| `q1` `INT_COL * 2 >= 900000` | `66.40 ms` | `67.61 ms` | `52.26 ms` | `53.22 ms` | `53.49 ms` |
| `q2` `LOW_CARD IN ('C0'..'C5')` | `67.59 ms` | `74.20 ms` | `58.50 ms` | `60.25 ms` | `63.63 ms` |
| `q3` `SUM(INT_COL)` 且 `INT_COL >= 400000` | `61.38 ms` | `63.81 ms` | `51.74 ms` | `51.96 ms` | `48.46 ms` |
| `q4` 7 项组合过滤 | `1262.80 ms` | `1002.89 ms` | `913.65 ms` | `941.88 ms` | `487.06 ms` |
| 墙钟时间 | `73,677 ms` | `61,263 ms` | `54,783 ms` | `56,410 ms` | `32,842 ms` |
| 读吞吐 | `43.4 QPS` | `52.2 QPS` | `58.4 QPS` | `56.7 QPS` | `97.4 QPS` |

`q4` 的完整文本：

```sql
SELECT COUNT(*) FROM T
 WHERE LOW_CARD <> 'C9' AND INT_COL >= 10000 AND DOUBLE_COL < 950
   AND TS_COL >= TIMESTAMP '2026-02-01' AND NULLABLE_COL IS NOT NULL
   AND CARDINALITY(ARRAY_COL) >= 1 AND CARDINALITY(STR_ARRAY_COL) >= 1
```

`q1`~`q3` 与记录值在换用最佳性能电源后基本吻合。`q4` 稳定在 `913 ms`~`945 ms`，为记录值的 1.9 倍，且不随写负载变化（无写线程 `941.88 ms` 与限速写 `913.65 ms` 一致），排除写路径与合并的影响。

同一场景连续两次运行的波动约为 ±5%（`q4` 两次为 `1262.80` / `1294.12 ms`），堆容量试验的波动约为 ±15%，判定阈值需在此之上。

## 三、已完成的方向

| 方向 | 机制 | 代码位置 |
| --- | --- | --- |
| 分批加锁与段级快路径 | `RowIterator.nextBatch` 在单次读锁内取回 512 行；`DeltaStore.hasSegmentDelta` 让无改动的段跳过逐行查表 | `ColumnarStore`、`DeltaStore`、`OmapCursor` |
| 列裁剪与延迟物化 | `LazyOmapRow` 仅在 `getValue(col)` 时解码该列 | `LazyOmapRow`、`ColumnSegment` |
| 低基数 `VARCHAR` 字典编码 | 建段时按基数决定，`int[] codes` + 预缓存 `Value[] dict` | `DictValueVector` |
| 空值位图快路径 | 全列无 null 时 `isNull` 直接返回 `false` | `NullBitmap` |
| 两阶段合并 | 锁外构建新段（Copy-On-Compact），锁内替换引用并按「rowId 加值」清理 delta | `ColumnarStore.compact`、`ColumnSegment.applyDelta`、`ZoneMap.tryUpdate` |
| 向量化下推（M7） | 替换 `Select` 与 `Comparison`，单表过滤与聚合按段整列执行 | `vectorized/` |
| 持久化与单 Jar（M8） | WAL 增量日志与增量列段快照 | `persistence/` |
| 数组列按元素列式存储 | 前缀和下标数组 + 拼接的元素列，`CARDINALITY` 退化为一次整数减法 | `ArrayVector`、`ColumnSegment`、`ValueCodec`、`VectorizedFilter` |
| 段级剪枝（M11） | 过滤条件的顶层 `AND` 给出每列上下界，快照按 `zone map` 跳过不相交的段，任何谓词都不在被跳过的段上求值 | `VectorizedFilter.collectBounds`、`ColumnarStore.takeVectorizedSnapshot(lower, upper)` |
| 有序 `LIMIT`（M11） | 段按排序列在 `zone map` 上的边界排序后依次扫描，容量为 `limit + offset` 的堆留下前 N 行，堆满后整段早停 | `OmapVectorizedExecutor.executeOrdered`、`Select.tryVectorizedFlat` |

向量化下推的效果可直接从本文数据读出：`q4` 在 1000 万行上单线程耗时为 `211 ms`（见 4.1），而 M7 之前的行式路径同一查询为 `2190 ms`。

## 四、定位：数组列没有列式布局

### 4.1 单线程拆解

单线程、无写线程、同一连接上把 `q4` 拆成多个变体，每条预热 2 次后计时 7 次取中位数：

| 变体 | 中位数 | 命中行数 |
| --- | --- | --- |
| `COUNT(*)` 无过滤 | `0 ms` | 10,000,000（走 `getRowCount`，不下推） |
| 5 个标量谓词 | `77 ms` | 7,380,415 |
| 5 个标量谓词 + `CARDINALITY(ARRAY_COL) >= 1` | `137 ms` | 6,643,951 |
| 完整 `q4` | `211 ms` | 5,314,466 |
| 仅 `CARDINALITY(ARRAY_COL) >= 1` | `146 ms` | 9,001,802 |
| 仅 `CARDINALITY(STR_ARRAY_COL) >= 1` | `168 ms` | 8,000,450 |
| 仅 `INT_COL >= 10000` | `19 ms` | 9,930,010 |
| `CARDINALITY(ARRAY_COL) >= 1 AND INT_COL >= 10000` | `104 ms` | 8,938,832 |

两个 `CARDINALITY` 谓词合计约占单线程耗时的 **62%**（`211 - 77 = 134 ms`）。它们在 `VectorizedFilter.CardinalityCmpNode` 中逐行执行：

```java
Value v = vec.get(idx);
if (v != ValueNull.INSTANCE && matchCard(v)) { ... }
// matchCard: ((ValueArray) v).getList().length 与常量比较
```

`getList()` 只返回字段（`ValueCollectionBase` 中是直接 `getfield`，无拷贝），但每行仍需三次依赖式引用跳转（元素槽位 → `ValueArray` 对象 → `Value[]` 头部），处理器无法提前预取。

按每行搬运的字节数折算，这两个谓词已经贴近单线程内存带宽上限：

| 谓词 | 单线程耗时 | 每行字节 | 有效吞吐 |
| --- | --- | --- | --- |
| 仅 `CARDINALITY(ARRAY_COL) >= 1` | `146 ms` | `144 B` | 约 `9.9 GB/s` |
| 仅 `CARDINALITY(STR_ARRAY_COL) >= 1` | `168 ms` | `216 B` | 约 `12.9 GB/s` |
| 仅 `INT_COL >= 10000` | `19 ms` | `4 B` | 约 `2.1 GB/s` |

### 4.2 并发下单位成本上升约 4 倍

| 场景 | 线程 | `q3` | `q4` |
| --- | --- | --- | --- |
| 单线程 | 1 | `35 ms` | `211 ms` |
| 只读压测 | 16 | `52 ms` | `884 ms`~`942 ms` |

服务端进程在读阶段的 CPU 占用为 **15~18 个核**（逐秒采样），不存在锁串行化，是真实并行。按 CPU 时间折算，16 读线程下单条查询平均占用约 `270 ms` 单核时间，而单线程 `q4` 仅需 `211 ms`。标量查询在两种场景下只差 1.5 倍，`q4` 差 4.3 倍。

原因是 `q4` 的数组列访问是跳 GB 规模的指针跳转，16 线程并发时内存子系统饱和（16 × 10 GB/s 已远超双通道内存的有效带宽）；标量列是连续数组，能获得缓存局部性与顺序访问的优势。

### 4.3 内存构成

1000 万行建完后 `jcmd GC.class_histogram` 的前 15 项（活对象合计约 5.5 GB，约 550 字节/行）：

| 类 | 实例数 | 占用 | 来源 |
| --- | --- | --- | --- |
| `Value[]` | 30,038,698 | `1,123.6 MB` | 每行 1 个行数组 + 每个数组列 1 个元素数组 |
| `ValueArray` | 20,000,001 | `610.4 MB` | 两个数组列各 1000 万个 |
| `byte[]` | 10,767,367 | `323.1 MB` | `String` 的底层存储 |
| `ValueTimestamp` | 10,000,241 | `305.2 MB` | `TS_COL` |
| `DefaultRow` | 10,000,013 | `305.2 MB` | 每行 1 个 |
| `ValueInteger` | 19,495,261 | `297.5 MB` | 数组元素与 `NULLABLE_COL` |
| `ValueVarchar` | 12,571,168 | `287.7 MB` | 数组元素 |
| `TypeInfo` | 8,105,555 | `247.4 MB` | 挂在 `ValueArray` 上 |
| `String` | 10,766,908 | `246.4 MB` | `VARCHAR` 列与 `STR_ARRAY_COL` 元素 |
| `long[]` | 2,015 | `239.9 MB` | `ID` 列 |
| `ValueBigint` | 10,038,835 | `229.8 MB` | 行数组中的 `ID` |
| `ValueDouble` | 10,000,307 | `228.9 MB` | 行数组中的 `DOUBLE_COL` |
| `Long` | 10,000,134 | `228.9 MB` | 主键索引的 rowId |
| `ConcurrentSkipListMap$Node` | 10,000,004 | `228.9 MB` | 主键索引条目 |
| `ConcurrentSkipListMap$Index` | 4,997,135 | `114.4 MB` | 主键索引跳表 |

`ValueArray`、其元素值（`ValueInteger` / `ValueVarchar`）与 `TypeInfo` 合计约 `1.4 GB`；若计入 `Value[]` 中属于数组元素的那部分（约三分之二），两个数组列相关对象约 `2.2 GB`，占活对象的 40%。主键索引（跳表节点、跳表索引与装箱 rowId）约 `0.57 GB`，占 10%。

`-Xmx6g` 下 GC 日志显示 72 次回收后仍存活 `5,527 MB`（堆上限 `6,144 MB`），单次暂停 5~10 ms。堆容量试验（16 读、无写线程、20 轮）：`-Xmx6g` 时 `q4` 为 `884.20 ms`，`-Xmx12g` 为 `654.27 ms`，`-Xmx20g` 为 `779.01 ms`，改善落在运行方差附近，**GC 不是主因**，但 `-Xmx6g` 对 1000 万行偏紧。1000 万行场景的堆默认值因此改为 `8g`（`scripts/final-benchmark.ps1`、`scripts/final-benchmark.sh`、`AGENTS.md` 同步）。

### 4.4 结论

`q4` 慢的根因是**数组列没有列式布局**：`ARRAY_COL` 与 `STR_ARRAY_COL` 以整值形式存放在 `ValueVector` 中，每行是一个 `ValueArray` 加一个 `Value[]` 加若干装箱元素，`CARDINALITY` 只能逐行指针跳转求值，占据单线程耗时的 62%；这批对象占活内存约 2.2 GB，16 线程并发时内存子系统饱和，单位成本再上升约 4 倍。

## 五、解决：数组列按元素列式存储

### 5.1 布局

`ArrayVector` 把一列拆成三部分：

| 组成 | 类型 | 含义 |
| --- | --- | --- |
| `starts` | `int[]`，长度 `行数 + 1` | 每行元素在 `elements` 中的起止下标，前缀和形式 |
| `elements` | `ColumnVector` | 按行顺序拼接的元素列，`IntVector` / `VarcharVector` 等 |
| `nulls` | `NullBitmap` | 整行为 NULL 的行；元素自身的 NULL 由 `elements` 的位图记录 |

`CARDINALITY` 变为 `starts[i+1] - starts[i]`；`CardinalityCmpNode.filterSegment` 对 `ArrayVector` 走专用分支，不再构造 `ValueArray`。`get(index)` 只在 H2 真正取到该行该列时按 `starts` 重建 `ValueArray`。

### 5.2 退回 `ValueVector` 的条件

`ArrayVector.tryBuild` 遇到下列任一情况返回 `null`，`ColumnSegment.build` 随即退回原来的 `ValueVector`，保证不丢信息：

- 列声明的元素类型带有扩展类型（`ExtTypeInfo` 非 null，例如嵌套数组），段快照无法序列化；
- 任一非 NULL 数组的元素值类型与列声明的元素类型不一致。

只比较元素的值类型，不比较精度与长度，原因有两处实测事实：

| 事实 | 表现 |
| --- | --- |
| 空数组的元素类型是 `NULL` | `ARRAY[]` 由 H2 构造成元素类型为 `NULL` 的值，与列的 `INTEGER` 不等 |
| 非空数组的元素类型比列声明的更窄 | `ARRAY['a','bb']` 的元素类型是 `CHARACTER VARYING(2)`，列声明是 `CHARACTER VARYING` |

若按 `TypeInfo.equals` 严格比较，含空数组或字符串数组的列会整列退回 `ValueVector`，优化静默失效。放宽后仍不丢信息：元素按列声明的元素类型还原，`ValueArray.get` 在同值类型时直接返回原值，转换不改变元素。

### 5.3 其它改动

| 位置 | 改动 |
| --- | --- |
| `ColumnSegment.build` | 参数由 `int[] valueTypes` 换成 `TypeInfo[] columnTypes`，便于取元素类型 |
| `ColumnarStore` | 保存 `columnTypes` 并在 `freeze()` 传入 |
| `ValueCodec` | 新增 `VEC_ARRAY`：元素类型三元组 + `starts` + 递归写元素向量 |
| `ZoneMap.of` | 数组列直接返回恒相交实例，不参与剪枝（算值域要重建每行 `ValueArray`，而数组值域几乎不能用于跳段） |
| `ArrayVector.set` | 新旧长度相同时就地改写元素；长度变化时重建整列（合并走 Copy-On-Compact，代价与那次复制同阶） |

### 5.4 结果（16 读、无写线程、20 轮、1000 万行、内存库）

| 指标 | 改动前 `-Xmx12g` | 改动后 `-Xmx8g` | 改动后 `-Xmx12g` |
| --- | --- | --- | --- |
| `q1` | `50.24 ms` | `46.68 ms` | `45.44 ms` |
| `q2` | `59.20 ms` | `54.50 ms` | `52.80 ms` |
| `q3` | `45.69 ms` | `43.89 ms` | `40.44 ms` |
| `q4` | `654.27 ms` | `163.39 ms` | **`159.60 ms`** |
| 墙钟时间 | `16,629 ms` | `6,227 ms` | `6,096 ms` |
| 读吞吐 | `77.0 QPS` | `205.6 QPS` | `210.0 QPS` |

同堆（12g）对比：`q4` 由 `654.27 ms` 降到 `159.60 ms`，降幅 **75.6%**；墙钟由 `16,629 ms` 降到 `6,096 ms`；吞吐由 `77.0` 升到 `210.0 QPS`。

`q1`~`q3` 两次改动后测量的差值（`1.2`~`3.5 ms`）与改动前到改动后的差值同量级，判定为运行噪声；堆容量 8g 与 12g 之间未见可辨识差异。

改动后单线程的 `q4` 未重测。按 4.1 的拆解推算，`CARDINALITY` 部分应从 `134 ms` 降到接近 0，剩下的成本是 5 个标量谓词的 `77 ms`。

## 六、解决：段级剪枝与有序 `LIMIT`（M11）

### 6.1 两种机制

两者都只复用已有的段级 `zone map`，不新增任何存储结构：

| 机制 | 触发条件 | 不命中时的行为 |
| --- | --- | --- |
| 段级剪枝 | 过滤条件的顶层 `AND` 里有「列与常量比较」的合取项 | `OR`、`<>`、`IN`、列上算术不产生区间，该列不参与剪枝 |
| 有序 `LIMIT` | `ORDER BY` 单列、排序键是被扫描表的列、`LIMIT` 为常量且 `limit + offset` 不超过 10000 | 多列排序、无 `LIMIT`、上限过大时交回 H2 行式路径与排序 |

同一列有多个合取项时只保留首次出现的界（区间取宽不取窄），因此不需要在收集阶段引入常量比较，也不会漏行。

### 6.2 真实实例的实测

生产表 `SEARCH_ROUTE_RESULT`：11 列、无任何索引、`55,541,500` 行，`CREATETIME` 按插入递增，区间约 18.9 小时。表在这批测量期间一直在增长：改动前的基线在 `43,784,000` 行上测得，段级剪枝部署后在 `45,336,000` 行上复测（当时往返中位 `159 ms`），本节「改动后」一列均为有序 `LIMIT` 部署后的 `55,541,500` 行。因此下面的降幅对改动后偏保守。

测量通道是 DBX 的 MCP 查询接口，单次往返有固定开销，因此先测基准 `SELECT 1`（三次均为 `117 ms`），再用「往返减去基准」估算引擎耗时。每条语句文本带不同微秒数，避免命中 H2 的查询结果缓存。每条查询测 3~6 次取中位，次数少时多测一次以确认抖动幅度。

| 查询 | 改动前往返 | 改动后往返 | 变化 |
| --- | --- | --- | --- |
| 2 小时窗口 + `WEBSITEID = 19`，`COUNT(*)` | `326 ms` | **`188 ms`** | −42% |
| 同上，窗口缩到 1 分钟 | `315 ms` | **`128 ms`** | −59% |
| 仅 2 小时窗口，`COUNT(*)` | `155 ms` | `142 ms` | −8% |
| 同条件取 100 行（无排序） | `341`~`367 ms` | **`129 ms`** | −63% |
| `ORDER BY CREATETIME DESC LIMIT 100` | `3,893`~`4,503 ms` | **`143 ms`** | −96.5% |
| `ORDER BY CREATETIME ASC LIMIT 100` | 未测 | `139 ms` | — |
| `ORDER BY CREATETIME DESC LIMIT 100 OFFSET 1000` | 未测 | `147 ms` | — |
| 仅 `WEBSITEID = 19`（无时间区间） | `387`~`414 ms` | `395`~`458 ms` | 无变化 |

三点判读：

- 时间窗口从 2 小时缩到 1 分钟，改动前耗时不变（两者均需全表扫描），改动后降到基准线（`128 ms` 往返），说明整段被跳过的部分不再产生任何求值。仅时间条件那一条只降了 `13 ms`，因为它在改动前已经靠在段内 `zone map` 上跳段，剪枝只是把同一件事提到了谓词求值之前。
- 不排序的取行查询也从 `341`~`367 ms` 降到 `129 ms`，这部分来自段级剪枝：`WEBSITEID` 只在与时间区间相交的段上求值。此前 `AndNode` 先跑 `WEBSITEID`（每段值域都含 8~21，剪不掉），在全表上做了一遍字典比较。
- `ORDER BY` 相对同条件不排序只多 `14 ms`（`143` 对 `129`），排序本身的开销已基本消失。

正确性校验（同一过滤条件）：`MAX(CREATETIME)` 为 `2026-11-18 09:32:05.994889`，`ORDER BY CREATETIME DESC LIMIT 100` 的首行同值，返回 `100` 行且单调递减，末行 `2026-11-18 09:32:05.66997`。

### 6.3 压测表上的数据

Apple M4 上 500 万行、16 读 + 1 写、50 轮三场景，查询集已包含 `q5`（`SORT_TS` 区间加低基数等值，`ORDER BY SORT_TS DESC LIMIT 100`）：

| 查询 | 不限速写 | 限速 50 轮/秒 | 文件数据库且限速 50 轮/秒 |
| --- | --- | --- | --- |
| `q1` | `34.47 ms` | `26.27 ms` | `27.10 ms` |
| `q5` | `14.07 ms` | `12.78 ms` | `13.07 ms` |

`q5` 与 `q1` 同量级且更低，说明 `SORT_TS` 的段间边界单调、段级早停确实发生；若边界不单调，`q5` 会退化为「扫完所有幸存段再排序」。完整的三个场景见 `BENCHMARK_RESULT.md`。

## 七、剩余方向

### 1. 行数组与主键索引的内存（中收益）

`DefaultRow` 与每行 `Value[]` 合计约 `0.7 GB`，主键索引约 `0.57 GB`，两者都与「按列」的方向相反。若全表扫描不再逐行构造行数组，前者可以显著削减。

### 2. `ArrayVector.get()` 的重复重建（低收益）

同一次查询内若多次读到同一行的数组列，每次都会重建一次 `ValueArray`。目前 H2 对一行的访问集中在 `LazyOmapRow` 的一次物化内，未观察到明显影响；若后续出现按行反复读取数组列的查询，可为 `get` 增加按行缓存。

### 3. 字典列的段级统计（中收益）

`WEBSITEID` 这类低基数列每段值域都含全部取值，`zone map` 剪不掉任何段，实例上单条件查询仍需 `290`~`460 ms`。要让这类列也能跳段，需要在建段时按值分布给出段级摘要（例如每段每个取值的行数，或一个位图），代价是每段多几十字节；收益取决于低基数列的查询频率，目前没有生产数据支撑这一判断。

### 4. 按排序列的块级稀疏索引（暂不需要）

若某表的插入顺序与排序列不同向，段级上界不单调，有序 `LIMIT` 的早停不会触发。此时可按每 512 行记录块的起始偏移与该块 `min(排序列)`，500 万行约 `1.4 MB`，把早停粒度从段降到块。现有两份实测（压测表 `q5` `12.78`~`14.07 ms`、实例上排序取页 `143 ms`）都显示早停已经生效，因此该方向暂不实施。

### 5. 已废弃的方向

原「`CARDINALITY` 长度独立列」不再需要：`ArrayVector.starts` 已完整给出每行的元素个数，单独再存一份 `int[] lengths` 会成为同一事实的两份来源。

## 八、复现方式

构建：

```bash
mvn -B package -DskipTests
```

一键压测（服务端堆默认 `8g`，`-ServerXmx` 可调；默认 500 万行、16 读线程、`50` 轮，查询集为 `q1`~`q5`）：

```bash
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/final-benchmark.ps1 -SkipBuild
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/final-benchmark.ps1 -SkipBuild -WriterRps 50
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/final-benchmark.ps1 -SkipBuild -WriterRps 50 -Persist
```

`scripts/final-benchmark.ps1` 内部调用 `mvn`，在 Windows 上会命中 `mvn.ps1` 包装脚本并在 `Set-StrictMode` 下因未定义变量抛错；先按上面的命令单独构建、再带 `-SkipBuild` 执行可绕过。该缺陷尚未修复。

5.4 的两组改动后数据不是由脚本产出，而是独立起服务端、再用纯 H2 客户端连接，形状与改动前 `-Xmx12g` 那次一致（16 读、无写线程、20 轮），便于同条件对比：

```bash
java -Xmx8g -cp target/h2omap-0.1.0-SNAPSHOT.jar org.h2.tools.Server -tcp -tcpPort 19098 -ifNotExists
java -Xmx3g -cp "<h2 jar>;target/test-classes" com.hyd.h2omap.bench.ConcurrentQueryBench \
  16 10000000 20 false omap \
  "jdbc:h2:tcp://127.0.0.1:19098/mem:q4g8;DB_CLOSE_DELAY=-1;QUERY_CACHE_SIZE=0" 0
```

4.1 的单线程拆解：同一服务端上把 `q4` 拆成各变体，每条预热 2 次、计时 7 次取中位数。该计时工具与 4.3 的堆容量试验脚本均为一次性使用，未纳入仓库。

6.2 的实例侧查询直接对生产表执行，两条语句如下（时间常量按查询条件代入，每次测量带不同微秒以免命中结果缓存）：

```sql
SELECT COUNT(*) FROM SEARCH_ROUTE_RESULT
 WHERE WEBSITEID = 19
   AND CREATETIME >= TIMESTAMP '2026-11-18 07:32:06'
   AND CREATETIME <= TIMESTAMP '2026-11-18 09:32:06';

SELECT * FROM SEARCH_ROUTE_RESULT
 WHERE WEBSITEID = 19
   AND CREATETIME >= TIMESTAMP '2026-11-18 07:32:06'
   AND CREATETIME <= TIMESTAMP '2026-11-18 09:32:06'
 ORDER BY CREATETIME DESC LIMIT 100;
```
