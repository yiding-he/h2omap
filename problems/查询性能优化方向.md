# OMAP 查询性能优化方向

状态：部分已实施（方向 1、2、3 及方向 4 的无 NULL 快路径已完成并验证，方向 5 为架构边界说明）。本文档记录 M5 阶段减少扫描查询耗时的优化方向与设计约束。

## 背景与基准现状

OMAP 面向纯内存 OLAP 扫描，同时允许查询期间并发执行高频细粒度写入（无表级锁与行锁，依赖 `ColumnarStore` 读写锁与创建时刻快照隔离并发读写）。

在当前完成 M4（索引区间查询）与标量子查询结果复用修复后，100 万行分引擎基准（`DataGenerator`，`-Xmx3g`，预热后 `TRUNCATE` 重插）对比结果如下：

| 指标 / 查询 | OMAP | MVStore |
| --- | --- | --- |
| 插入耗时 / 插入后堆占用 | 1511 ms / 623 MB | 1004 ms / 1069 MB |
| `SELECT COUNT(*) FROM T WHERE LOW_CARD = 'C3' AND INT_COL > 500000` | 221 ms | 87 ms |
| `SELECT SUM(INT_COL) FROM T WHERE INT_COL > 500000`（读 1 列） | 196 ms | 82 ms |
| `SELECT * FROM T WHERE INT_COL > 500000`（读 9 列） | 210 ms | 54 ms |
| `SELECT COUNT(*) FROM T WHERE INT_COL > (SELECT AVG(INT_COL) FROM T)` | 443 ms | 270 ms |

1000 万行 OMAP 单引擎（`-Xmx12g`）7 字段组合条件 `COUNT(*)` 耗时 3943 ms（命中 5,314,466 行，占比 53.14%）。

数据显示，当前 OMAP 在全表扫描查询上普遍慢于 MVStore 1.5~3 倍，且只读 1 列（196 ms）与读取全部 9 列（210 ms）耗时几乎没有差异。以下五个方向按预期收益与实施优先级排序。

## 优化方向

### 1. 分批加锁拉取与段级无 delta 快路径（高收益）

**现状与瓶颈**：
- `OmapCursor.next()`（`src/main/java/com/hyd/h2omap/index/OmapCursor.java:46-54`）每推进一行都会先后触发两次 `lock.readLock()` 加解锁：一次在 `SegmentRowIterator.next()`（`ColumnarStore.java:417`），一次在 `store.materialize(rowId)`（`ColumnarStore.java:234`）。
- 对已冻结段，`materialize` 每次都会调用 `delta.getUpdated(rowId)` 与 `delta.isSegmentRowDeleted(rowId)`（`HashMap`/`HashSet` 查找）。
- 在 1000 万行全表扫描中，这会带来 2000 万次读写锁 CAS 操作与千万次哈希表查找。

**改进方案**：
- **分批加锁（Chunked Read）**：将迭代与物化合并为批量拉取方法，在 `OmapCursor` 内部维护一个小批量缓冲区（例如每批 512 或 1024 行）。每次进入一次 `readLock` 连续提取一批可见行引用，随即释放读锁。锁次数降至原来的 `1/500 ~ 1/1000`，同时单批持锁时间在数十微秒级，**不会在几秒的查询期间阻塞并发写入线程**。
- **段级无 delta 快路径**：维护每个段在 `delta` 中的变更标记（或段级 dirty 计数）。当某个段既无更新也无删除记录时，批读取直接顺序访问该段列向量，跳过每行的 `HashMap`/`HashSet` 查找。

**实施状态与实测收益（已完成）**：
- 改动文件：`DeltaStore.java`（新增 `dirtySegments` 与 `hasSegmentDelta`）、`ColumnarStore.java`（`RowIterator.nextBatch` 在单次 `readLock` 内批读取与物化，及 `materialize` 快路径）、`OmapCursor.java`（`BATCH_SIZE = 512` 批量消费）。
- 100 万行（`DataGenerator 1000000 ... omap`，`-Xmx3g`）：查询耗时稳定下降 **15%~32%**（`LOW_CARD = 'C3' AND INT_COL > 500000` 由 221 ms 降至 167 ms；`LOW_CARD = 'C3' AND INT_COL > 500000 AND DOUBLE_COL < 900` 由 200 ms 降至 145 ms；`SELECT * WHERE INT_COL > 500000` 由 210 ms 降至 142 ms）。
- 1000 万行（`DataGenerator 10000000 ... omap`，`-Xmx12g`）：7 字段组合过滤由 3943 ms 降至 3333 ms（-15.5%），`SUM(INT_COL)` 由 3897 ms 降至 3097 ms（-20.5%）；在 6+ GB 堆占用下全行物化带来的 GC 压力占主导，进一步加速需依赖方向 2 与方向 3。

### 2. 列裁剪与延迟物化 `LazyRow`（高收益）

**现状与瓶颈**：
- `ColumnSegment.getRow(offset)`（`src/main/java/com/hyd/h2omap/storage/ColumnSegment.java:83`）无条件分配 `new Value[columns.length]` 并解码全表所有列。
- 即使 SQL 只引用 1 列（如 `SELECT SUM(INT_COL)`），其余 8 列（含 `Varchar`、`Timestamp`、`ARRAY_COL`、`STR_ARRAY_COL`）仍会全部完成解码与装箱。

**改进方案**：
- **延迟行对象（`LazyOmapRow extends Row`）**：`org.h2.result.Row`（`.h2/main/org/h2/result/Row.java`）是 `public abstract class`。游标返回延迟行对象，仅持有目标段的只读视图与段内 `offset`（或 `delta` 行引用）；当 H2 表达式求值调用 `getValue(col)` 时，才按列索引从对应的 `ColumnVector` 解码。
- **收益**：
  1. 未被引用的列全程不解码、不装箱；
  2. 多条件 `AND` 过滤短路时，前面条件已淘汰的行不再物化后续列；
  3. 仅在 H2 调用 `getValueList()`（如进入 `LocalResult`）时才补齐数组，遵守「不就地修改已交出的 `Value[]`」契约。
- **并发约束**：若采用延迟解码，需保证该段在持锁批读取后、行被 H2 消费完毕前，底层列向量不被 `compact()` 原地覆写，或由批读取在锁内将批内涉及的段行引用/所需列值安全提取。

**实施状态与实测收益（已完成）**：
- 改动文件：`LazyOmapRow.java`（继承 `Row` 按列延迟解码）、`ColumnSegment.java`（新增 `applyDelta` 实现 Copy-On-Compact）、`ColumnarStore.java`（`compact()` 替换新段引用，读路径返回 `LazyOmapRow`）、`NullBitmap.java` 及各 `ColumnVector`（新增 `copy()`）。
- 100 万行（`DataGenerator 1000000 ... omap`，`-Xmx3g`）：多数过滤与聚合查询耗时降至 **20~116 ms**（较方向 1 后再降 **50%~80%**），超越纯内存 MVStore 基准；查询结束堆占用由 1134 MB 降至 736 MB。
- 1000 万行（`DataGenerator 10000000 ... omap`，`-Xmx12g`）：组合过滤与聚合提速 **3x~12.5x**（如 `NULLABLE_COL = 123456` 由 2781 ms 降至 223 ms，`INT_COL * 2 > 1000000` 由 3066 ms 降至 401 ms，`SUM(INT_COL)` 由 3097 ms 降至 628 ms，标量子查询由 9538 ms 降至 1297 ms）。

### 3. 低基数 `Varchar` 字典编码与 `Value` 实例复用（中-高收益）

**现状与瓶颈**：
- `VarcharVector`（`src/main/java/com/hyd/h2omap/vector/VarcharVector.java:14`）直接以 `String[]` 存放原始字符串，每次 `get(index)` 都调用 `ValueVarchar.get(values[index])` 创建 `ValueVarchar` 实例。
- 对于 `LOW_CARD`（10 个取值）这类低基数列，100 万行扫描会重复分配 100 万个 `ValueVarchar` 对象，且字符串引用分散在堆中。

**改进方案**：
- 在段冻结构建时统计列基数，低于阈值（如基数 < 段行数的 10% 或固定上限）时启用段内字典编码：底层以紧凑的 `int[]`（或 `short[]`/`byte[]`）存字典下标，字典表直接预缓存 `ValueVarchar[]`。
- 读路径 `get(index)` 直接返回 `dictValues[dictIds[index]]`，实现零 `Value` 对象分配并改善 CPU 缓存局部性。
- 写入合并（`compact()`）触及新字符串时，支持将新值追加进字典，或超过基数阈值时退化回 `VarcharVector`。

**实施状态与实测收益（已完成）**：
- 改动文件：`DictVarcharVector.java`（`int[] codes` + 预缓存 `Value[] dict`，支持 `tryBuild`、`copy()`、`set()` 动态追加字典项）、`ColumnSegment.java`（建段时对 `CHAR`/`VARCHAR` 试探字典编码，基数上限 `min(4096, max(64, count / 4))` 超过即回退 `VarcharVector`）。
- 100 万行：`LOW_CARD = 'C3' AND INT_COL > 500000` 由 68 ms 降至 **39 ms**；`LOW_CARD IN ('C1'..'C5')` 由 57 ms 降至 **39 ms**；`SELECT * WHERE INT_COL > 500000` 由 146 ms 降至 **118 ms**。
- 1000 万行：`LOW_CARD IN ('C1'..'C5')` 由 494 ms 降至 **350 ms**（-29.1%）；`GROUP BY LOW_CARD HAVING ...` 由 1137 ms 降至 **852 ms**（-25.1%）；7 字段组合过滤由 2437 ms 降至 **2190 ms**；查询结束堆占用由 9357 MB 降至 8520 MB。

### 4. 减少数值列装箱与空值位图查表（中收益）

**现状与瓶颈**：
- `IntVector` / `LongVector` / `DoubleVector` 每次 `get(index)` 都要执行 `nulls.isNull(index)` 位运算，然后调用 `ValueInteger.get` / `ValueBigint.get` / `ValueDouble.get` 进行装箱（H2 仅对小整数做了缓存，大整数与浮点每次都需要分配对象）。

**改进方案**：
- **无 NULL 快速路径**（已实施）：`NullBitmap` 维护 `hasNull` 标记，全列无 null 时 `isNull(index)` 直接返回 `false`，跳过数组读取与位运算。
- 配合方向 2 的延迟物化，减少非必要列与被前置条件过滤行的装箱总量。

### 5. `ZoneMap` 剪枝与执行器天花板说明

- **现状**：`OmapScanIndex.find` 通过 H2 的 `SearchRow` 提取上下界做 `ZoneMap` 段级剪枝。对按时间或单调主键聚簇的数据，剪枝可跳过大部分段；但对完全随机分布的列，段内 min/max 区间基本重合，无法跳过段。
- **已知天花板**：H2 的 SQL 执行引擎采用行式火山模型（`Expression.getValue(SessionLocal)` 逐行求值），不修改 H2 源码就无法下推批量列向量算子（SIMD / 段级位图过滤）。前四个方向的优化目标是将存储层自身的锁、物化与对象分配开销压至最低，逼近 H2 执行器本身的耗时下限（M6 判决点）。
