# 列编码与压缩：阶段性实施计划

状态：草案，待确认。分支 `feature/column-encoding`，基于 `main` @ `638de12`。

## 0. 目标与边界

目标只有一个：**相同数据量下，用更少的内存完成更快的查询**。具体化为三个可量测的量：

| 量 | 现状（现网 `POLICY_OW`，829 万行 × 11 列） | 目标 |
| --- | --- | --- |
| 段内容驻堆字节（`residentBytes` 管的量） | 5.5 GB，与磁盘段文件大小几乎相等（无压缩） | 第一阶段降 2–4 倍（取决于列形态） |
| 段文件磁盘读量 | 逐出段按需读回按原始字节读，单线程约 65 MB/s | 第一阶段降 3–5 倍 |
| 页缓存可容纳的段内容 | 30 GB 内存装 9.9 GB 段文件（两表） | 同等页缓存装 3–5 倍数据 |

不在本计划内（已评估、单独立项或不做）：

- 主键 `rowId` 索引的内存紧凑化（`ConcurrentSkipListMap<Long, Long>`，5,700 万行约 4–5 GB，是单项最大的堆开销，但它不属于列式存储，是 H2 UPDATE/DELETE 契约的代价）。
- 段内排序与编码协同（sort-order / 聚簇）。它是编码之上的第二级收益，等第一阶段的编码收益实测后再决定。
- 查询语义、H2 替换面、`AGENTS.md` 里的任何契约：全部不动。编码与压缩只改变值的字节表示，不改变任何查询结果。

## 1. 现状：差距在代码里的落点

| 现状 | 位置 | 含义 |
| --- | --- | --- |
| 数值向量是定宽原始数组 | `vector/IntVector.java:15`（`int[]`）、`LongVector`（`long[]`）、`TimestampVector`（两个 `long[]`，16 B/值） | 每值固定 4 或 8 B，与取值范围无关 |
| 字典码是 `int[]` | `vector/DictVarcharVector.java:24`（`codes`）、`DictValueVector` 同构 | 字典基数 10 的列每行仍占 4 B，而 10 个取值只需 4 bit |
| 字典容量上限 `min(4096, max(64, 行数/4))` | `storage/ColumnSegment.java:119` | 码值域最多 12 bit，位打包后每码 1.5 B |
| 列块无压缩直写 | `persistence/OmapPersistence.java:763` `writeSegment()`，列块按 `VEC_*` 原始字节顺序存放 | 磁盘大小 = 驻堆大小，页缓存密度无放大 |
| `ValueCodec` 的 10 种 `VEC_*` 标签 | `persistence/ValueCodec.java:41-51` | 编码标签是列块首字节，有加新标签的空间 |
| 向量化路径按 `instanceof XxxVector` 分发并直接读原始数组 | `vectorized/` 下 11 个文件、61 处；读法是 `vec.rawValues()` 取 `int[]`/`long[]` 后按选择向量批量扫（`ColCmpNode.java:102`） | **这是计划里最重要的约束**：新编码不能作为新向量类型直接插入，否则 61 处分发都要补分支 |
| 全量读把整段读进 `byte[]` 再解码 | `OmapPersistence.java:1040-1058` | 解码期间文件缓冲与向量同时驻堆，瞬时双份 |
| 格式版本化 + 启动自动升级 | `MANIFEST_MAGIC_V3`/`SEGMENT_MAGIC_V3`、`FORMAT_VERSION = 3`、v2→v3 升级在 `recover()` 内 | 本计划走同一套演进路径：v3 → v4 |

## 2. 设计原则

1. **编码态与查询态分离**：向量在堆上有两种形态——**编码态**（位打包 / 字典码 / 压缩页，用于驻留、逐出判定、磁盘读写）与**查询态**（原始 `int[]`/`long[]`，供现有 61 处向量化分发零改动地读）。查询态按批解包到**可复用的线程局部缓冲**，不复制整列。
2. **不新增向量类型**：`IntVector`/`LongVector`/`DictVarcharVector` 等类的公开契约不变（`rawValues()`、`nulls()`、`get(int)`、`size()`），只在内部把「数组字段」换成「编码字段 + 惰性解码」。向量化路径、行式路径、`ValueCodec`、`ColumnSlice` 都不需要知道编码存在。
3. **编码在建段时决定、按列独立选择**：与现有「字典编码按基数决定」同一位置（`SegmentBuilder` 冻结时）、同一口径。候选编码按「估算编码后字节数最小」选，全不划算则退回原始数组——与字典向量「超出上限退回普通向量」一致。
4. **磁盘格式只做一次 v4 升级**：编码标签进列块首字节之后的第二字节（或扩展现有 `VEC_*` 标签空间），列块内容按编码序列化；压缩是编码之外的正交层（每个列块整体压缩，首字节记压缩算法）。manifest 与段文件各升一次版本，升级路径复用 v2→v3 的「并行读入 + 原子写回 + 幂等重入」。
5. **收益用现网数据实测，不用合成数据**：每个阶段结束都在 server30 的 `POLICY_OW` 上量测三个目标量，数字进 `BENCHMARK_RESULT.md`；判定依据仍是现有 165 个用例加新增的编码往返与升级用例。

## 3. 阶段划分

### 阶段 A：位打包与字典码压缩（预计改动最集中、收益最确定）

范围：

- `DictVarcharVector` / `DictValueVector` 的 `codes` 从 `int[]` 改为按 `ceil(log2(字典大小))` 位打包；字典大小为 1 时退化为「全同值 + null 位图」，零码字。
- `IntVector` / `LongVector` 新增两种编码（按列独立选择）：**`BitPacked(width)`**（按列最大位宽打包，适用于值域窄的 `INT` 列、状态列）与 **`Delta`**（相邻差值后再位打包，适用于 `ID`、时间戳类单调列）。`TimestampVector` 的两个 `long[]` 各自独立编码。
- 查询态按批解包：`rawValues()` 的语义改为「返回整列解包后的数组」会破坏内存目标，因此新增 **按批读接口**（`readBatch(startRow, count, destBuffer)`），向量化路径的 61 处 `rawValues()` 循环改为按 512 行（与 `OmapCursor` 批大小一致）推进；线程局部 `int[]`/`long[]` 缓冲复用，堆增量是每线程 2–4 KB。
- 驻留记账 `getEstimatedMemory()` 按编码后字节数计，`residentBytes` 预算自然获得收益。

明确不做：`DoubleVector`（`Gorilla`/`Chimp` 类浮点编码复杂度高、现网 `DOUBLE_COL` 占比小，留到阶段 C 评估）；行式路径的 `get(int)` 单点读走即时解包（性能与原始数组接近，不单独优化）。

验收：
- 新增用例：每种编码的往返（`ValueCodecTest`）、编码选择判定（`ColumnarStoreTest`：构造窄值域列断言选了 `BitPacked`、构造随机 32 位列断言退回原始）、位宽边界（字典大小恰为 2^k）、含 NULL 列、`rawValues()`/`readBatch()` 与原始数组逐值一致。
- 变异验证：编码选择恒选原始 / 位宽算错 / `Delta` 差分方向反 / 解包缓冲不复用（断言分配次数）。
- 现网实测：`POLICY_OW` 驻堆字节与 `residentBytes` 账本对比，预期 `LOW_CARD` 列降 8 倍、`ID` 列降 3–4 倍，全表 2–4 倍。

### 阶段 B：列块压缩 + 格式 v4 + 启动升级

范围：

- 列块级压缩：`writeSegment()` 对每个编码后的列块整体压缩，首字节记算法（`0 = 无`，`1 = LZ4` 或 `Deflater`，取决于依赖决策）；`readSegment()`/`readSegmentColumns()` 透明解压。压缩在编码之后，两层正交。
- 压缩库决策（需您拍板，见第 5 节）：零依赖路线用 JDK `java.util.zip.Deflater`（`Deflater.BEST_SPEED` 级别），速度约为 LZ4 的 1/3–1/2，但无传递依赖；引库路线候选 `lz4-java`（零传递依赖、约 300 KB）或 `zstd-jni`（零传递依赖、约 4 MB 含多平台本地库）。
- 格式 v4：段文件魔数 `OSG4`、manifest `OMAPS`、`FORMAT_VERSION = 4`；列目录每项增加「编码 + 压缩算法 + 编码后长度」。v3 → v4 升级复用 v2 → v3 的并行读入 + 原子写回 + 幂等重入路径；升级时按当前编码规则重新选择编码（存量段在 v3 下全是原始数组，升级即完成首次编码）。
- 临时缓冲：全量读改为按列块流式读（先读尾部目录，再逐列块读 + 解压 + 解码），`byte[] fileBytes` 整段缓冲消失，瞬时堆峰值从「文件大小 + 向量」降到「最大单列块 + 向量」。

验收：
- `SegmentUpgradeTest` 新增 v3→v4 用例（升级正确、幂等重入、损坏拒绝）、`SegmentFileFormatTest` 新增压缩往返与「压缩列块的部分列读只解压请求列」用例。
- 现网实测：段文件总大小、逐出段读回耗时、冷查询（`jcmd` 清页缓存后）的 `read_bytes`。

### 阶段 C：段内分页与页级剪枝（依赖 A、B）

范围：

- 列块切成固定行数的页（候选 8192 行，与 ClickHouse granule 对齐，现网段 6.5 万行约 8 页）；尾部目录为每页登记偏移、压缩后长度与页级 zone。页是压缩、编码与读的最小单位。
- `VectorizedFilter` 的区间剪枝从段级下沉到页级；`readSegmentColumns` 只读相交页。
- 这一步把剪枝粒度从 6.5 万行细化到 8192 行，对 `WHERE CREATETIME > x` 这类时间窗查询直接减少读量，是「更快」维度上本计划唯一的查询路径改动。

验收：页级剪枝用例（构造跨页边界谓词，断言只读相交页的 IO 统计）、页级 zone 与段级 zone 一致性、现网时间窗查询 IO 对比。

### 阶段 D（可选）：`DoubleVector` 浮点编码

仅在阶段 A–C 完成后、现网 `DOUBLE_COL` 占比仍显著时启动。候选 `Chimp`（比 Gorilla 简单、对 double 效果稳定）。

## 4. 每阶段的交付物与提交粒度

与既有里程碑一致：

- 实现 + 契约/存储/格式用例 + 变异验证 + 全量 165 用例通过 + `AGENTS.md` 同步（存储设计、持久化格式、判定依据计数）+ `BENCHMARK_RESULT.md` 现网数字。
- 每阶段三笔提交（feat / test / docs），阶段内不混提。
- 阶段 B 与 C 都改磁盘格式，但只升一次版本：B 定 v4 的目录结构时预留页表字段，C 填充；若 C 不能紧随 B，则 C 单独升 v5。这一点在 B 开始前定。

## 5. 需要您决策的事项

| # | 决策 | 推荐 | 理由 |
| --- | --- | --- | --- |
| 1 | 压缩库：`Deflater`（零依赖）还是引入 `lz4-java` / `zstd-jni` | **`lz4-java`**：零传递依赖、单 Jar 约 300 KB（含多平台本地库）、解压速度是 `Deflater` 的 3–5 倍，压缩比略低但对已编码数据差别小 | `Deflater` 的解压速度会成为逐出段读回的新瓶颈（65 MB/s 的磁盘地板解除后 CPU 成为主项）；`zstd-jni` 压缩比更高但 4 MB 且首次加载慢，对 OLAP 扫描不划算 |
| 2 | 向量化路径 61 处 `rawValues()` 的改法：按批解包 vs 编码态直接计算 | **按批解包** | 编码态直接算（如位打包上直接比较）每处都要重写、且随机访问解包慢；按批解包把 61 处改动收敛为「循环外层加一层批」的机械改动，查询态仍是原始数组 |
| 3 | 阶段 A 的 `Delta` 编码是否首期就做 | **做** | 现网 `ID`、`TS_COL`、`SORT_TS`、`CREATETIME` 都是单调或近单调列，`Delta` 收益比 `BitPacked` 大；但实现只比 `BitPacked` 多一次差分，不构成独立风险 |
| 4 | 阶段 C 是否进入本计划 | **进入，但排在 B 之后、以 B 的现网数字决定是否执行** | 页级剪枝是「更快」维度唯一实质改动，但它改查询路径、风险高于 A/B；若 B 之后冷查询已满足目标，C 可推迟 |
| 5 | 编码后是否对 `ValueVector` 回退向量也做处理 | **不做** | `ValueVector` 只承接 `JSON`、几何、`BLOB` 等不可比较类型，现网表没有这类列 |
| 6 | 存量 v3 段升级时是否强制重选编码 | **强制** | v3 段全是原始数组，升级是唯一一次全量重写机会；不强制则存量段永远享受不到编码，只对新冻结段生效 |

## 6. 风险与回退

| 风险 | 应对 |
| --- | --- |
| 按批解包在窄查询（点查、`LIMIT 1`）上比原始数组慢 | 点查走行式路径的 `get(int)` 即时解包，单值解包是常数时间；`LIMIT` 查询仍按段整列扫，批解包开销与原始数组同阶 |
| `Delta` 编码对乱序列（`KEY1` 的哈希、`HIGH_CARD`）为负收益 | 建段时按「编码后字节数最小」选，负收益自动退回原始数组，不会误选 |
| 升级期间双份内存（v3 段读入 + v4 段写出） | 与 v2→v3 升级同形态：按段流水、4 线程并行、写完即释放；现网 9.9 GB 一次升级约 3–5 分钟，窗口内驻留预算照常生效 |
| `lz4-java` 本地库在 server30（Linux x86_64、JDK 17）加载失败 | 阶段 B 第一步先在 server30 做 `Loader.load()` 验证；失败则回退 `Deflater`（算法字节预留，运行时可选） |
| 变异验证发现覆盖缺口 | 按 #2219 先补断言再复测，不放宽用例 |

## 7. 判定依据与验收口径

- 既有 165 个用例全部保持通过，计数不变；新增用例进 `ValueCodecTest`、`ColumnarStoreTest`、`SegmentFileFormatTest`、`SegmentUpgradeTest`。
- 每阶段现网量测三项（驻堆字节、段文件大小、逐出段冷读耗时），数字进 `BENCHMARK_RESULT.md`，与阶段前对比。
- 性能取舍按 `AGENTS.md`「面向 OLAP」原则：接受快场景适度放宽，优先压慢场景（逐出段读回、冷段全表扫描）。
