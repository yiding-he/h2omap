# 标量子查询结果复用：定位与修复

状态：结果复用已修复（提交 `d95345d`）；M10 与 S5 已把单表 `WHERE` 里的不相关标量子查询、不相关 `IN`/`EXISTS`、关联 `EXISTS`、关联标量聚合、关联 `IN`/`NOT IN` 折进向量化下推。本文档保留定位过程、各轮实测与仍未覆盖的形态。

## 摘要

在 OMAP 表上执行标量子查询（如 `WHERE INT_COL > (SELECT AVG(INT_COL) FROM T)`）时，
子查询会按外层结果集的行数重复执行，导致耗时随外层行数线性放大。
1 万行实测 12.8 秒；100 万行基准在该条上超时（工具 600 秒上限）。同样的查询在 H2 默认 MVStore 表上耗时 12 毫秒。

根因不在 OMAP 的 SQL 执行（OMAP 不实现执行器），而在 H2 的结果缓存判定：
OMAP 表的修改 ID 与 H2 全局修改 ID 是两套独立计数，前者远大于后者，
使得 `Query` 的「结果可复用」判定恒为假，子查询每次被调用都重新执行。

## 环境

以下为缺陷定位时的环境。

- h2omap：`target/classes`，commit 工作区（M4 完成后）
- H2：2.5.252，源码在仓库 `.h2/` 目录
- JVM：`-Xmx2g`，内存库 `jdbc:h2:mem:...;DB_CLOSE_DELAY=-1`
- 数据：`bench/DataGenerator`，1 万行，`segmentSize=1000`，`compactionMinRows=1000`

## 现象

查询：

```sql
SELECT COUNT(*) FROM T WHERE INT_COL > (SELECT AVG(INT_COL) FROM T)
```

实测（1 万行）：

| 表引擎 | 内层 `SELECT AVG(INT_COL) FROM T` 单独执行 | 整条查询 |
| --- | --- | --- |
| OMAP | 14 ms | 12819 ms |
| MVStore | — | 12 ms |

对照查询 `SELECT COUNT(*) FROM T WHERE INT_COL > 250000`（常量阈值，无子查询）在 OMAP 上 6 ms。

## H2 的执行路径

以下行号均在仓库 `.h2/main/org/h2/` 下。核对依赖本地 `.h2/` 目录，当前环境该目录不在，行号未经二次复核；H2 版本固定为 `2.5.252`。

1. 子查询求值入口是 `Subquery.getValue`（`expression/Subquery.java:44`）：

   ```java
   try (ResultInterface result = query.query(2)) { ... }
   ```

   每次调用都执行 `query.query(2)`，自身不缓存。外层每行调用一次。

2. H2 会尝试在优化期把子查询替换为常量，但只对 `isConstantQuery()` 为真的查询生效
   （`expression/Subquery.java:99-105`）：

   ```java
   query.prepare();
   if (query.isConstantQuery()) {
       return ValueExpression.get(getValue(session));
   }
   ```

   `Select.isConstantQuery`（`command/query/Select.java:1785`）对含 `FROM` 子句或聚合的查询返回 false：

   ```java
   if (!super.isConstantQuery() || distinctExpressions != null || condition != null || isGroupQuery
           || isWindowQuery || hasFromClause()) {
       return false;
   }
   ```

   具体地，`Select.java:1786` 的判定包含 `isGroupQuery` 与 `hasFromClause()`。
   `SELECT AVG(INT_COL) FROM T` 是聚合查询且带 `FROM`，因此 `isConstantQuery()` 为 false，
   常量替换不发生。`getIfSingleRow`（`Select.java:1795`）同样返回 null。

3. 因此子查询的执行次数完全由 `Query.query` 的结果复用决定
   （`command/query/Query.java:521`）。复用条件在 `Query.java:537-540`：

   ```java
   if (lastResult != null && !lastResult.isClosed()
           && isStable && maxDataModificationId <= lastEvaluated
           && limit == lastLimit && sameParameters(params, lastParameters)
           && Arrays.equals(inPredicateSortTypes, lastInPredicateSortTypes)) {
       lastResult = lastResult.createShallowCopy(session);
       ...
   }
   ```

   缓存写入条件在 `Query.java:551`：`isStable && maxDataModificationId <= now`。
   两个条件都要求 `maxDataModificationId` 不超过会话侧的修改 ID。

4. `Query.getMaxDataModificationId`（`Query.java:911`）：

   ```java
   return Math.max(visitor.getMaxDataModificationId(), session.getSnapshotDataModificationId());
   ```

   其中 `visitor` 收集各表 `Table.getMaxDataModificationId()` 的最大值。

## 根因

OMAP 表的修改 ID 与 H2 全局修改 ID 是两套互不相干的计数。

- `OmapTable.getMaxDataModificationId`（`src/main/java/com/hyd/h2omap/table/OmapTable.java:222`）
  返回 `store.getDataModificationId()`，即 `ColumnarStore` 的 `AtomicLong dataModificationId`
  （`storage/ColumnarStore.java:63`），每次 `append` 自增（`ColumnarStore.java:672`）。
  插入 1 万行后该值为 10000。

- 会话侧的修改 ID 来自 H2 的 `Database.modificationDataId`
  （`engine/Database.java:166`），只在 H2 自身的数据修改中递增。
  `SessionLocal.getStatementModificationDataId`（`engine/SessionLocal.java:1746`）
  返回语句开始时的 `database.getModificationDataId()`（`SessionLocal.java:1696`）。
  OMAP 的写入不经过 H2，因此该值不反映 OMAP 的修改，且数值远小于 OMAP 的 10000。

- 于是 `Query.getMaxDataModificationId()` 取两者较大值后为 10000，
  而 `lastEvaluated` / `now` 是 H2 的全局 ID（远小于 10000），
  `maxDataModificationId <= lastEvaluated` 恒为假，缓存既不写入也不命中。

对照 MVStore：`MVTable` 在写入时调用 `database.getNextModificationDataId()`
（`mvstore/db/MVTable.java:659`），其 `getMaxDataModificationId` 与 `database.modificationDataId`
同系，判定成立，子查询结果被复用，整条查询 12 毫秒。

## 影响范围

- 所有标量子查询（`WHERE col > (SELECT ...)`、`SELECT (SELECT ...)`、`IN (SELECT ...)` 的求值路径）在 OMAP 表上都会按外层行数重复执行。
- 只要查询涉及 OMAP 表，`Query` 的结果复用就不生效；同一语句重复执行时也不会复用中间结果。
- 聚合查询、`GROUP BY`、`ORDER BY` 等不带子查询的查询不受此问题影响；其中「其结果集缓存同样不生效」一句描述的是修复前的状态，修复后不成立。

## 修复方向（当时的评估记录）

方向 1 已按下节「实际修复方案与验证结果」实施，方向 2 未采用。

1. 让 OMAP 的修改 ID 与 H2 全局修改 ID 同系：在 OMAP 写路径（`OmapTable.addRow` /
   `removeRow` / `updateRows`）调用 H2 公开的 `Database.getNextModificationDataId()`
   （`engine/Database.java:442`），并让 `getMaxDataModificationId()` 返回该值。
   需要验证：写入后缓存立即失效的时序、并发写下的单调性、以及 `isStable` /
   `isUpdatedInCurrentTransaction` 是否随之成立。
2. 或者让 OMAP 表不参与 `Query` 的结果复用路径，接受每行执行，但需在文档中明确限制。

方向 1 的已知风险：`getMaxDataModificationId` 的语义是「数据修改的严格上界」，
若与 H2 全局 ID 混用，需保证 OMAP 每次写入都递增全局 ID，否则 H2 可能命中过期缓存。

## 实际修复方案与验证结果

### 补充定位

原分析只涉及了 `Query.java:537-551` 的修改 ID 比较，遗漏了前置门禁 `Query.getNoCache()`（`Query.java:474`）：

- `Query.getNoCache()` 调用 `isEverything(ExpressionVisitor.DETERMINISTIC_VISITOR)`。
- `Select.isEverything`（`Select.java:1707`）检查参与表的 `Table.isDeterministic()`。
- 当 `OmapTable.isDeterministic()` 返回 `false` 时，`noCache` 直接为 `true`，查询根本不会进入 `maxDataModificationId` 的缓存写入与复用路径。

因此，**仅同步 `getMaxDataModificationId()` 无法解决子查询重复执行问题**，必须同时将 `OmapTable.isDeterministic()` 改为 `true`。

### 改动说明

1. **`src/main/java/com/hyd/h2omap/table/OmapTable.java`**：
   - 将 `isDeterministic()` 改为返回 `true`，由 `getMaxDataModificationId()` 负责缓存失效。
   - 新增 `lastModificationId`（`AtomicLong`）与 `syncLastModificationIdWithDatabase()`，参照 `MVTable`（`mvstore/db/MVTable.java:658-675`）调用 `database.getNextModificationDataId()` 并通过 CAS 单调更新，防止并发写时版本号倒退。
   - 在 `addRow`、`removeRow`、`truncate`、`updateRows` 的存储与索引写入完成**之后**调用 `syncLastModificationIdWithDatabase()`（`addRow` 与 `updateRows` 置于 `finally` 块，避免部分写入回退期间并发读以新版本号缓存旧数据）。
   - `getMaxDataModificationId()` 改为返回 `lastModificationId.get()`。

2. **`src/test/java/com/hyd/h2omap/OmapTableContractTest.java`**：
   - 新增 `scalarSubqueryReusesResultAndInvalidatesOnWrite`，验证 `WHERE` 标量子查询、`SELECT` 投影标量子查询、`EXISTS (SELECT ...)`、`IN (SELECT ...)` 在 `INSERT` / `UPDATE` / `DELETE` / `TRUNCATE` 后缓存均正确失效。

3. **`src/test/java/com/hyd/h2omap/bench/DataScaleTest.java`**：
   - 新增 `scalarSubqueryMatchesMvStoreAndReusesResult`（1 万行，`segmentSize=1000`），验证 OMAP 与 MVStore 查询结果及耗时。

4. **`AGENTS.md`**：
   - 同步更新 `Table.isDeterministic()`、`getMaxDataModificationId()` 的契约说明与用例计数。

### 验证结果

执行 `mvn -B -q package && mvn -B test`：

- 50 个启用测试当时全部通过（`OmapTableContractTest` 34 个、`ColumnarStoreTest` 10 个、`ValueVectorTest` 3 个、`DataScaleTest` 3 个；`DataScaleLargeTest` 1 个按配置跳过）。当前为 `OmapTableContractTest` 43 个、`ColumnarStoreTest` 15 个、`ValueVectorTest` 3 个、`DataScaleTest` 3 个，合计 64 个启用、1 个跳过。
- 1 万行 `SELECT COUNT(*) FROM T WHERE INT_COL > (SELECT AVG(INT_COL) FROM T)` 实测：**OMAP 5 ms（count=4397），MVStore 4 ms（count=4397）**（修复前为 12819 ms）。
- 100 万行 `DataScaleLargeTest` 未开启运行（`-Domap.scale=large`，未验证）。

## 修复之后：仍未优化的形态（M10 之前的基线）

`d95345d` 之后，不相关标量子查询的内层查询不再按外层行数重算。但含子查询的 `WHERE` 在向量化下推里仍然整体失效，大表上仍不可用。

以下为 100 万行单表、单线程的实测（M10 之前）。一次性测量程序直接驱动 `DataGenerator.generateSingle`，`segmentSize=65536`、`compactionMinRows=16384`、`QUERY_CACHE_SIZE=0`，每条预热 2 次后计时 7 次取中位数：

| 形态 | SQL 要点 | 中位数 | 命中行数 |
| --- | --- | --- | --- |
| 常量阈值（向量化下推） | `WHERE INT_COL > 250000` | `3 ms` | 750,283 |
| 不相关标量子查询 | `WHERE INT_COL > (SELECT AVG(INT_COL) FROM T)` | `134 ms` | 500,303 |
| 投影中的子查询 | `SELECT (SELECT MAX(INT_COL) FROM T) FROM T LIMIT 1` | `12 ms` | 1 行输出 |
| 关联 `EXISTS` | `WHERE EXISTS (SELECT 1 FROM T T2 WHERE T2.ID = T.ID)` | `716 ms` | 1,000,000 |
| 关联标量子查询 | `WHERE INT_COL > (SELECT AVG(INT_COL) FROM T T2 WHERE T2.LOW_CARD = T.LOW_CARD)` | 中止（超过 10 分钟） | — |

三条机制：

1. **下推失效。** `OmapVectorizedExecutor.tryExecuteFlat`（`OmapVectorizedExecutor.java:107`）把 `condition` 交给 `VectorizedFilter.compile`，后者没有 `Subquery` 分支，返回 `null` 即放弃整个下推，查询退回 H2 的行式求值。同为单列过滤，常量阈值的 `3 ms` 与子查询的 `134 ms` 之差主要来自这一条。
2. **结果复用的固定成本仍按行计。** 缓存命中时 `Query.query(2)` 要校验复用条件并 `createShallowCopy`，`Subquery.getValue` 再取一行，约 `134 ns/行`；1000 万行对应秒级，而等价的常量阈值是二三十毫秒。
3. **关联子查询无专门处理。** 代价完全取决于内层能否走索引：`T2.ID = T.ID` 走主键唯一索引点查，`716 ms/100 万行`；`T2.LOW_CARD = T.LOW_CARD` 无索引，外层每行一次全表扫描，100 万行超过 10 分钟未完成。

`IN (SELECT ...)` 的一次测量（`80 ms`）中子查询结果为空集，测的是空集路径，不代表 `IN` 的普遍代价，不计入结论。

结论：**子查询的执行方式与代价不可接受。** `WHERE col > (SELECT ...)` 在 1000 万行下是秒级，等价的常量阈值是二三十毫秒；关联子查询在不建索引时不可用。

配套的机制分析（后文「缺陷清单」的前身）：H2 优化器只有 `isConstantQuery()` 覆盖 `SELECT` 字面量的极窄情形（`Select.java:1830`），读表的子查询一律不折叠；关联子查询无去关联化，代价完全取决于内层能否走索引；含 `GROUP BY` 的派生表按可参数化视图处理，JOIN 改写反而更慢（1 万行实测：子查询 4.2 s，内联 JOIN 改写 5.3 s，两步先物化再 JOIN 0.69 s）。

## M10：子查询下推（已实施）

### 缺陷清单

| # | 缺陷 | 机制（H2 `2.5.252`） | 基线实测（100 万行单线程） |
| --- | --- | --- | --- |
| D1 | 不相关标量子查询不折叠 | 只有 `isConstantQuery()` 折成 `ValueExpression`，读表的子查询每行付 `query(2)` 校验 + 浅拷贝 + 取行 ≈ 134 ns/行 | 134 ms vs 常量阈值 3 ms |
| D2 | 关联子查询无去关联化 | 内层对外层每行求值一次，无子查询改写 | 1 万行 3.5 s，O(n²)；100 万行外推 ≈ 9.8 小时 |
| D3 | 派生表谓词下推使 JOIN 改写失效 | 含 `GROUP BY` 的派生表按可参数化视图处理，`EXPLAIN` 显示 `?1`/`?2` 参数化重执行 | 见上文两步物化实测 |
| D4 | `IN (SELECT)` 逐行二分 | 每行 `containsDistinct` 对排序结果二分 | 大集合 691 ms，小集合 118 ms（同形状对照，M10 后重测） |
| D5 | `EXISTS` 依赖索引 | 逐外层行执行内层；无索引列 O(n²) | 主键等值 716 ms；无索引列不可用 |

### 方案与实施

路线选择：在向量化入口层预计算（S 系列），不改 H2 优化器（H 系列挂起）。理由：灾难形态（D2/D5）全部落在单表 `WHERE`，正是本引擎的目标负载；每步独立可验收、回退安全；H 系列的通用收益真实但要永久承担升级移植。

| 步骤 | 形态 | 实现 |
| --- | --- | --- |
| S1 | 不相关标量子查询在比较一侧 | `isFoldableConstant` 遍历子查询表达式判定是否引用被扫描表，不引用即编译期一次求值当常量；整型列遇带小数常量由 `integerBound` 收敛到整数边界 |
| S2 | 不相关 `IN (SELECT)` | 一次求值收进集合；整数列用原始 `long` 开放寻址集合（`LongSet`），其余用 `Value` 哈希；空集折成恒假/恒真，子查询含 NULL 且 `NOT IN` 折成恒假 | 替换 `ConditionInQuery` 公开 `getLeft()`/`isNot()`/`isAll()`/`getCompareType()` |
| S3 | 关联标量聚合 | 内层表 `takeVectorizedSnapshot` 一次预计算「关联键 → 聚合结果」，外层按关联键哈希查找后比较；`GroupAgg` 口径对齐 H2 `AggregateDataDefault`/`AggregateDataAvg` |
| S4 | 关联 `EXISTS`/`NOT EXISTS` | 预计算关联键集合折成半连接节点；不相关 `EXISTS` 常量化 |

共同边界：内层单表 OMAP 查询、无 `ORDER BY`/`LIMIT`/`OFFSET`/窗口、恰好一个等值关联、其余合取项只引用内层表；不识别一律交回 H2 行式路径。代码在 `vectorized/SubqueryFold.java`，由 `VectorizedFilter.compile` 末尾与 `compileComparison` 调用。

### 实测结果（100 万行单线程，预热 2 次取 7 次中位数，`QUERY_CACHE_SIZE=0`）

| 查询 | M10 之前 | M10 之后 |
| --- | --- | --- |
| `V > (SELECT AVG(V) ... WHERE T2.K = T.K)`（整数关联键） | 外推 ≈ 9.8 小时 | **11 ms** |
| 同上（varchar 关联键） | 不可测 | **26 ms** |
| `EXISTS (... WHERE T2.ID = T.ID)`（主键） | 716 ms | **42 ms** |
| `EXISTS (... WHERE T2.LOW_CARD = T.LOW_CARD)`（无索引列） | O(n²) 不可用 | **10 ms** |
| `INT_COL IN (SELECT ...)`（50 万元素大集合） | 691 ms | **453 ms** |
| `TAG IN (SELECT ...)`（10 元素小集合） | 118 ms | **1 ms** |
| `V > (SELECT AVG(V) FROM T)`（不相关） | 134 ms | **≈0 ms**（S1，先行提交） |

验证：`OmapTableContractTest` 新增 5 个用例（`inSubqueryFoldsIntoSetPredicate`、`correlatedAggregateFoldsIntoPrecomputedGroups`、`correlatedExistsFoldsIntoSemiJoin`、`unsupportedCorrelatedShapesFallBackToRowPath`、`correlatedAggregateFasterThanNestedLoop`），全部与 MVStore 等价查询比对结果；耗时用例断言 1 万行 < 200 ms（未折叠实测 2.7 s）。变异验证：禁用 `compileCorrelatedCmp` 后耗时用例失败（2706 ms），半连接节点改恒真后语义用例失败——「该折叠的确实折叠、折叠结果正确」都有用例把守。全量 `mvn -B test`：73 通过、0 失败、1 跳过。

### S5：关联 IN / NOT IN (SELECT ...)（已实施）

M10 只覆盖到关联 `EXISTS` 与关联标量聚合，关联 `IN (SELECT ...)` 一直交回 H2 嵌套循环：
外层每行执行一次内层查询，内层关联列无索引时是 O(n²)。基线实测（1 万行、单线程）：

| 查询 | 结果 |
| --- | --- |
| `X IN (SELECT ID FROM T2 WHERE T2.K = T.K)`（关联列无索引） | 7,231 ms，100 万行等比例外推不可用 |
| 同形状、关联列为主键（走 `OmapRowIdIndex` 点查） | 41 ms |
| 对照：S4 折叠后的单关联 `EXISTS`（100 万行） | 10 ms |

实现（`SubqueryFold.compileCorrelatedIn`，2026-01 本分支）：与 S3/S4 同一前提（内层单表
OMAP、恰好一个等值关联、无 `ORDER BY`/`LIMIT`/`OFFSET`/窗口），另要求内层投影是内层表的
列引用。编译期对内层表 `takeVectorizedSnapshot` 一次，建「归一化关联键 → 内层值集合」；
外层每行按键取集合做成员判定。整数族值列走原始 `long` 集合，字典键列按码预解析集合引用
（复用 S3 的 `normalizeKey` 与字典码路径）。`NOT IN` 按 SQL 三值语义：外层值为 NULL、
集合含 NULL 且外层值不在集合中（UNKNOWN）、外层值在集合中，三种情况都不命中；NULL 键与
未命中键按内层空集处理（`IN` 不命中、`NOT IN` 命中）。内层没有任何非 NULL 键时折成常量。
过程中修掉一个自身缺陷：`VectorizedFilter.LongSet` 原为固定容量（`InNode` 按最终大小一次
性建，从不触顶），逐步增长的调用方满槽后开放寻址会死循环，已补按元素数扩容。

实测（100 万行、单线程、预热 2 次取 7 次中位数）：`SELECT COUNT(*) FROM T WHERE X IN
(SELECT T2.ID FROM T T2 WHERE T2.K = T.K)`（命中 19,999 行）中位数 **84 ms**（75–87 ms）；
未折叠时 1 万行即 2,528 ms。判定用例：`correlatedInFoldsIntoKeyedSets`（整数与 varchar 关联
键、NULL 键、内层投影含 NULL、内层常量谓词、表达式投影回退，与 MVStore 逐行一致）、
`correlatedInFasterThanNestedLoop`（1 万行 < 200 ms，期望值由 MVStore 表独立对照）。变异验证：
禁用 `compileCorrelatedIn` 后耗时用例失败（2,528 ms）。

### 仍未覆盖的形态

- 投影里的子查询、`JOIN` 条件里的子查询、多表查询里的关联子查询：仍走 H2 行式路径。
- 关联 `IN (SELECT ...)` 的投影为表达式、多关联条件时不折叠，交回 H2（单列等值关联、内层投影为列引用的形态已折叠，见上文 S5）。
- 多关联条件、关联键为表达式、内层 `HAVING`/`GROUP BY`/`DISTINCT`/窗口、内层非 OMAP 表：回退。
- 关联聚合限 `COUNT(*)`/`COUNT`/`SUM`/`MIN`/`MAX`/`AVG` 且 `SUM`/`AVG` 参数为整数列；浮点与十进制求和口径、`COUNT(DISTINCT)`、聚合参数为表达式时不折叠。
- 大集合 `IN` 的剩余成本在内层子查询的行式执行与 `LocalResult` 物化（50 万行 ≈ 400 ms），要再快需要向量化执行内层查询，未列入计划。
- H2 优化器自身的去关联化（D2 的通用解）与派生表参数化修复（D3）未动。
